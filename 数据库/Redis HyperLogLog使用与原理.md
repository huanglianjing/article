# 1. 简介

在互联网业务中，经常需要统计"不重复元素的数量"，例如：

- 某个页面每天有多少独立访客（UV）
- 某个搜索框每天有多少个不同的搜索词
- 某个 App 的日活跃用户数（DAU）

这类问题叫做**基数统计（Cardinality Counting）**。数据量小时，用 Set 去重即可。数据量达到千万、亿级后，精确去重的内存开销会变得很大。

Redis 从 2.8.9 版本开始提供 **HyperLogLog（HLL）**。它在标准误差约 0.81% 的前提下，最多只用 **12KB** 内存，就能估算接近 2^64 个不同元素的基数。

假设要统计一个网站每天的 UV，日访问用户约 1 亿。常见方案对比如下：

| 方案        | 思路                  | 1 亿用户的内存占用（估算）      | 是否精确       |
| ----------- | --------------------- | ------------------------------- | -------------- |
| Set         | 存储所有用户 ID       | 数 GB（取决于 ID 长度和编码）   | 精确           |
| Bitmap      | 用户 ID 映射到 bit 位 | 约 12.5MB（要求 ID 为连续整数） | 精确           |
| HyperLogLog | 概率估算              | **约 12KB**                     | 标准误差 0.81% |

HyperLogLog 用一点精度换来了几个数量级的空间节省。在 UV 这类允许少量误差的场景中，它通常是最合适的选择。

HyperLogLog 的特点：

1. **内存固定且极小**：单个 key 最多约 12KB，与元素数量无关。
2. **只统计数量，不存储元素**：无法取出元素，也无法判断某个元素是否存在。
3. **可合并**：多个 HLL 可以无损合并，得到并集的基数估计。
4. **有误差**：标准误差为 0.81%。

# 2. 使用

HyperLogLog 命令前缀是 `PF`，取自发明者 Philippe Flajolet 的姓名首字母。

HyperLogLog 在 Redis 中以 **String 类型**存储。`TYPE` 命令返回 `string`，也可以用 `GET` / `SET` 读写原始字节，方便备份和迁移。

**PFADD 添加元素**

```redis
PFADD key element [element ...]
```

- 将一个或多个元素加入 HyperLogLog。
- 如果内部的估计结构发生了变化，返回 `1`，否则返回 `0`。
- 时间复杂度：每个元素 O(1)。

返回 0 不能 100% 说明元素"已经存在"，只能说明内部寄存器没有变化。新元素也可能不改变任何寄存器。

**PFCOUNT 获取基数估计值**

```redis
PFCOUNT key [key ...]
```

- 传入单个 key 时，返回该 HLL 的基数估计值。时间复杂度为 O(1)。
- 传入多个 key 时，返回这些 HLL **并集**的基数估计值，Redis 会在内存中临时合并，不修改原有 key。时间复杂度为 O(N)，N 为 key 的数量。

**PFMERGE 合并多个 HLL**

```redis
PFMERGE destkey sourcekey [sourcekey ...]
```

将多个 HLL 合并后写入 `destkey`。如果 `destkey` 已存在，它本身也会参与合并。

# 3. 原理

![](https://article-1304941664.cos.ap-guangzhou.myqcloud.com/database/redis_hyperloglog.jpg)

## 3.1 数学原理

HyperLogLog 的核心思想可以概括为一句话：**用哈希值中"连续 0 的最大长度"来推测元素个数**。

**基数统计**

反复抛一枚均匀硬币，直到出现正面为止，记录抛掷次数 k。

- k = 1 的概率是 1/2
- k = 2 的概率是 1/4
- k = n 的概率是 1/2^n

如果某人告诉你，他做了若干轮这样的实验，**最大的 k 是 10**，你可以推测他大约做了 2^10 ≈ 1024 轮。

把每个元素经过一个均匀的哈希函数，得到一个二进制串。可以把这个串看成一串硬币：0 代表反面，1 代表正面。

```
hash("user1") = ...0010110 1000   → 从低位起第 4 位第一次出现 1，记 ρ = 4
hash("user2") = ...1101001 0010   → ρ = 2
hash("user3") = ...0111000 0001   → ρ = 1
```

记录所有元素中 ρ 的最大值 **ρ_max**，则基数估计约为 **2^ρ_max** 。
这种方法有两个关键性质：

- **相同元素的哈希值相同**，重复添加不影响结果，天然去重。
- 只需保存一个很小的整数 ρ_max。对于 64 位哈希，它最大不超过 64，**用 6 个 bit 就能存下**。这也是 "LogLog" 名字的由来：存储空间是 log(log(n)) 级别。

**分桶平均**

单个 ρ_max 的方差很大，可能会有很大误差。

解决办法是**分桶**：

1. 取哈希值的前（或低）p 位作为桶编号，共 m = 2^p 个桶。
2. 用剩余的位计算 ρ，每个桶只记录本桶的最大 ρ，记为 M[j]。
3. 最后综合所有桶的值进行估算。

**调和平均**

LogLog 算法对各桶使用**算术平均**，而HyperLogLog（Flajolet 等，2007）改用**调和平均**，对离群的大值更不敏感。

Redis 使用低 14 位进行分桶，有 m = 2^14 = 16384 个桶。

大约 68% 的情况下误差在 ±0.81% 以内，约 95% 的情况下在 ±1.62% 以内。

**小基数与大基数修正**

原始 HLL 公式在基数很小时偏差较大，原因是大量桶仍为 0。

当基数很小时，Redis 默认使用稀疏表示，只记录非零寄存器的信息。一个空 HLL 仅占约 2 字节，内存占用也远低于 12KB。当元素增多到一定活出现较大计数值时，才会自动转换为稠密格式。

当基数非常大时，主要风险是哈希碰撞导致估计值偏低。Redis 使用 **MurMurHash64** 将元素映射为 64 位哈希值，使得在可预见的基数范围内，碰撞概率低到几乎可以忽略。

## 3.2 实现细节

Redis 的 HLL 实现位于源码 `src/hyperloglog.c`。

HyperLogLog 使用 MurmurHash64A 哈希函数对元素计算 64 位哈希值，然后用低 14 位确定桶编号（即有 2^14 = 16384 个桶），然后用剩余 50 位计算 ρ。

**元素写入**

一个元素对应的桶编号由低 14 位决定，例如低 14 位是 `00000000000101`，就选中 **5 号桶**。

将一个元素转化为 ρ，它等于剩下 50 位里从低位数连续 0 的个数加一。

```c
// 简化后的 hllPatLen 逻辑
uint64_t hash = MurmurHash64A(ele, elesize, 0xadc83b19ULL);
long index = hash & HLL_P_MASK;          // 低 14 位 -> 桶编号 (0~16383)
hash >>= HLL_P;                          // 去掉低 14 位，剩余 50 位
hash |= ((uint64_t)1 << HLL_Q);          // 在第 50 位放一个哨兵 1，保证循环终止
uint64_t bit = 1;
int p = 1;
while ((hash & bit) == 0) {              // 从低位开始数连续的 0
    p++;
    bit <<= 1;
}
// p 即 ρ，范围 1~51
```

将元素的 ρ 和对应桶的当前最大 ρ 值对比，如果更大则更新对应桶的 ρ 值。

```c
M[5] = max(M[5], p)
```

HyperLogLog 汇总 16384 个桶（也叫寄存器）的记录，再通过统计公式估算去重数量。

**存储结构**

一个 HLL 对象在内存中是一个 Redis 字符串，结构如下：

![](https://article-1304941664.cos.ap-guangzhou.myqcloud.com/database/redis_hyperloglog_store.jpg)

Header 共 16 字节。

- `HYLL`：魔数，用于识别合法的 HLL 对象。
- `encoding`：编码方式，0 表示稠密（dense），1 表示稀疏（sparse）。
- `notused`：3 字节保留位。
- `card`：8 字节的**基数缓存**，最高位为 1 表示缓存失效。HLL 对象产生修改时被标记为无效，统计时将值写入并标记为有效。

对于稠密编码，使用 6bit 记录一个桶（寄存器）的值，16384 个桶总共 12KB。

对于基数比较少时，默认使用稀疏编码，此时绝大多数寄存器都是 0，使用如下的操作码来表示：

* `ZERO`：格式为 `00xxxxxx`，用 1 字节表示连续 1-64 个寄存器为 0；
* `XZERO`：格式为 `01xxxxxxxxxxxxxx`，用 2 字节表示连续 1~16384 个寄存器为 0；
* `VAL`：格式为 `1vvvvvxx`，用 1 字节表示连续 1~4 个寄存器值为 v（v 取 1~32）；

如一个全空的 HLL，所有寄存器都是 0，用 1 个 XZERO 即可表示所有寄存器的状态，数据部分只有 2 字节。一个只插入了一个元素的 HLL，所有寄存器中只有一个为 1，如中间的某个，用 XZERO + VAL + XZERO 即可表示所有寄存器的状态，数据部分为 5 字节。

当某个寄存器的值超过 32（无法用 `VAL` 来表示），或者稀疏表示的字节数超过配置项 `hll-sparse-max-bytes`（默认 3000 字节）时，Redis 就会将其转换为稠密编码，且无法逆转。

**合并**

HyperLogLog 合并非常简单：**对每个桶取最大值**。

# 4. 最佳实践

**适用场景**

适合：UV、DAU/MAU、独立 IP 数、不同搜索词数量等**允许少量误差的大规模去重计数**。

不适合：需要精确数值的场景（如计费、对账），需要判断元素是否存在的场景（用 Bloom Filter 或 Set），需要取出元素明细的场景。

**合理设计 key 粒度**

按天建 HLL，周或月的数据通过 `PFCOUNT k1 k2 ...` 或 `PFMERGE` 得到，不必重复记录。

高频查询的周、月数据建议用 `PFMERGE` 固化结果，避免每次多 key 现场合并。

**多 key 操作**

`PFCOUNT` 多 key 和 `PFMERGE` 要求所有 key 位于同一个 slot，Redis Cluster 中可以使用 hash tag 来控制它们映射到同一个 slot。

```
uv:{page123}:20240601
uv:{page123}:20240602
```

大批量多 key 执行 `PFCOUNT` 比较耗时，容易阻塞 Redis 主线程。

`PFADD` 支持一次传入多个元素，配合 pipeline 能显著提升吞吐。
