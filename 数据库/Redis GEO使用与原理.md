# 1. 简介

Redis 从 3.2 版本开始提供 GEO 模块，用一组简单的命令完成地理位置的存储、距离计算和范围检索，并且性能也很好。

处理地理位置数据的实际场景有"附近的人"、"附近的门店"、"司机派单"、"外卖配送范围判断"等。

# 2. 命令详解

Redis GEO 模块相关命令如下：

| 命令                | 版本                    | 作用                           |
| ------------------- | ----------------------- | ------------------------------ |
| `GEOADD`            | 3.2                     | 添加或更新位置                 |
| `GEOPOS`            | 3.2                     | 获取成员的经纬度               |
| `GEODIST`           | 3.2                     | 计算两个成员之间的距离         |
| `GEOHASH`           | 3.2                     | 获取成员的 GeoHash 字符串      |
| `GEORADIUS`         | 3.2（6.2 起不推荐使用） | 以经纬度为中心做半径查询       |
| `GEORADIUSBYMEMBER` | 3.2（6.2 起不推荐使用） | 以成员为中心做半径查询         |
| `GEOSEARCH`         | 6.2                     | 统一的检索命令，支持圆形和矩形 |
| `GEOSEARCHSTORE`    | 6.2                     | 检索并把结果存入新 key         |

Redis 没有提供 `GEODEL` 命令，删除需要用 `ZREM`。

**GEOADD 添加位置**

给某个 key 添加指定经纬度和成员名称，一次添加一到多个位置。

```redis
GEOADD key [NX | XX] [CH] longitude latitude member [longitude latitude member ...]
```

- `longitude`：经度，范围 `-180 ~ 180`；
- `latitude`：纬度，范围 `-85.05112878 ~ 85.05112878`；
- `NX`：只添加新成员，不更新已存在的成员；
- `XX`：只更新已存在的成员，不添加新成员；
- `CH`：返回值改为"发生变化的成员数"，包括新增和坐标被修改的成员（6.2 起支持）。

纬度范围不是 ±90°，是因为 Redis 沿用了 Web 墨卡托投影（EPSG:3857）的范围，极地附近的坐标会被拒绝。

**GEOPOS 查询坐标**

查询某个 key 的一到多个成员坐标。

```redis
GEOPOS key member [member ...]
```

返回的坐标和写入时的坐标有微小差异，这是 GeoHash 编码造成的精度损失。

**GEODIST 计算距离**

查询某个 key 两个成员的距离。

```redis
GEODIST key member1 member2 [M | KM | FT | MI]
```

单位支持米（m，默认）、千米（km）、英尺（ft）、英里（mi）。

**GEOHASH 获取 GeoHash 字符串**

返回某个 key 的某个成员的 11 位标准 Base32 GeoHash 字符串。

```redis
GEOHASH key member
```

**GEOSEARCH 范围检索**

在某个 key 中以一个成员或指定坐标为起点，根据圆形或矩形搜索相近成员并返回，支持排序和数量限制。

```redis
GEOSEARCH key
    <FROMMEMBER member | FROMLONLAT longitude latitude>
    <BYRADIUS radius <M|KM|FT|MI> | BYBOX width height <M|KM|FT|MI>>
    [ASC | DESC]
    [COUNT count [ANY]]
    [WITHCOORD] [WITHDIST] [WITHHASH]
```

- **中心点**：`FROMMEMBER` 用已有成员作中心，`FROMLONLAT` 用指定坐标作中心；
- **范围形状**：`BYRADIUS` 表示圆形，`BYBOX` 表示矩形，矩形以中心点为中心；
- **排序**：`ASC` 按距离由近到远，`DESC` 由远到近；
- **数量**：`COUNT n` 限制返回条数。加上 `ANY` 后，找到 n 个结果就立即返回，不保证是最近的 n 个，但速度更快；
- **附加信息**：`WITHCOORD` 返回坐标，`WITHDIST` 返回距离，`WITHHASH` 返回 52 位整数形式的 GeoHash。

Redis 6.2 之后推荐用 `GEOSEARCH` 代替 `GEORADIUS` 和 `GEORADIUSBYMEMBER`，之前的版本没有 `GEOSEARCH`，只能用 `GEORADIUS` 系列命令。

**GEOSEARCHSTORE 检索结果落地**

查找方式和参数和 `GEOSEARCH` 类似，但是区别是会将结果存储到目标 key 中，返回存储的成员数量。

```redis
GEOSEARCH dest_key src_key
    <FROMMEMBER member | FROMLONLAT longitude latitude>
    <BYRADIUS radius <M|KM|FT|MI> | BYBOX width height <M|KM|FT|MI>>
    [ASC | DESC]
    [COUNT count [ANY]]
    [STOREDIST]
```

默认存储的是成员的原始 GeoHash 值，如果带上 `STOREDIST` 可选参数则存储的是表示距离的浮点数。

**ZSET 命令**

GEO 的底层是 ZSET，因此 ZSET 命令都能用。

```redis
ZREM shops 王府井   # 删除成员
ZCARD shops        # 统计成员数
ZSCORE shops 故宫   # 查看 52 位整数编码
TYPE shops         # 返回 zset
```

# 3. 原理

Redis GEO 的实现可以概括为一句话：**用 GeoHash 把二维经纬度编码成一维的 52 位整数，作为 score 存入有序集合 ZSET，再利用 ZSET 的有序性做范围查询。**

使用 52 位整数来表示一个 GEO 的值，是因为 ZSET 的 score 是 **IEEE 754 双精度浮点数（double）**，它的尾数有 52 位，加上隐含位，能精确表示 2^53 以内的所有整数。这使得 GeoHash 能够高效无损地存入 double 类型的 score。

## 3.1 编码

地理坐标是二维的 `(lng, lat)`，以经度 `116.397128`、纬度 `39.916527` 为例。

**第一步：对经纬度分别做二分编码**

对经度进行多次二分化缩小区间，经度区间 `[-180, 180]`，每次二分值落在左半区记 0，落在右半区记 1。

| 轮次 | 区间         | 中点   | 116.397 在哪侧 | 比特 |
| ---- | ------------ | ------ | -------------- | ---- |
| 1    | [-180, 180]  | 0      | 右             | 1    |
| 2    | [0, 180]     | 90     | 右             | 1    |
| 3    | [90, 180]    | 135    | 左             | 0    |
| 4    | [90, 135]    | 112.5  | 右             | 1    |
| 5    | [112.5, 135] | 123.75 | 左             | 0    |
| …    | …            | …      | …              | …    |

纬度用同样的方法处理，Redis 使用的纬度区间是 `[-85.05112878, 85.05112878]`。

Redis 对经度和纬度**各做 26 次**二分，分别得到 26 位二进制数。

**第二步：交叉合并**

把经度位和纬度的各 26 位交替排列，合并成 52 位。

```
经度位：  L1    L2    L3    L4    ...   （共 26 位）
纬度位：     A1    A2    A3    A4 ...   （共 26 位）
合并后：  L1 A1 L2 A2 L3 A3 L4 A4 ...   （共 52 位）
```

两个经纬度合成的 52 位数，每一位相同就相当于被分到了同样的半个经度或纬度区间，相同前缀的位数越长表示经纬度位置越接近。

**第三步：Base32 编码**

Redis 存储 GEO 的值会保存一个 52 位的整数。

当需要将这个值用于 GEOHASH 命令展示时，把二进制每 5 位一组，映射为 `0-9b-hjkmnp-z` 共 32 个字符，然后得到一个长度为 11 的字符串，如 `wx4g0gyz5r0`。

**精度**

精度和纬度的编码精度可以通过计算得出：

| **指标**           | **经度**      | **纬度**                     |
| ------------------ | ------------- | ---------------------------- |
| 有效范围           | -180° ~ 180°  | -85.05112878° ~ 85.05112878° |
| 编码位数           | 26 bit        | 26 bit                       |
| 可划分区间         | 2²⁶ ≈ 6711 万 | 2²⁶ ≈ 6711 万                |
| 角度分辨率         | 0.0000053644° | 0.0000025347°                |
| 赤道附近空间分辨率 | 约 0.597 米   | 约 0.282 米                  |

Redis GEO 存储坐标的精度在**亚米级**，对绝大多数 LBS 业务完全足够。

`GEOPOS` 返回的是解码后格子的**中心点**，所以和原始输入有极小的偏差。

## 3.2 存储

地理坐标的经纬度信息转换为一个 52 位整数后，保存在一个 ZSET key 成员的 score 里。

GEO 的几个特性：

- `GEOADD` 就是 `ZADD`，时间复杂度 O(log N)；
- 对同一个 member 再次 `GEOADD` 会覆盖 score，也就是更新坐标；
- 不需要单独的删除命令，直接用 `ZREM`；
- 成员数较少时，底层会使用 listpack（7.0 之前为 ziplist）紧凑编码，节省内存。

## 3.3 计算

**距离计算**

`GEODIST` 以及范围查询中的距离判断，使用的是 **Haversine（半正矢）公式**，把地球视为正球体，半径取 `6372797.560856` 米：

```
a = sin²(Δlat/2) + cos(lat1) · cos(lat2) · sin²(Δlng/2)
d = 2R · arcsin(√a)
```

真实地球是椭球体，因此距离计算存在**最多约 0.5%** 的误差。对"附近的人"这类场景无关紧要，但不适合测绘、精准计费等对距离要求严格的场景。

**范围查询**

`GEOSEARCH` 的核心流程如下：

* 根据半径估算 GeoHash 精度：不同位数的 GeoHash 对应不同大小的格子。Redis 会根据搜索半径，找一个**格子边长刚好不小于半径**的精度；
* 计算中心格子及其 8 个邻居：仅查中心点所在的格子是不够的，目标点可能落在相邻格子，因此 Redis 会计算 **中心格 + 8 个邻居 = 9 个格子**。由于格子边长不小于半径，这 9 个格子一定能完整覆盖整个搜索圆。Redis 还会做一些优化，剔除明显不与搜索区域相交的邻居格子，减少无效扫描；
* 把每个格子转换成 score 区间：**一个格子内的所有点在一维上是连续的**，于是"查一个格子"就变成了 ZSET 上的一次区间查询：`ZRANGEBYSCORE key min max`；
* 精确过滤：格子是方的，搜索区域是圆形，Redis 会对每个候选点用 Haversine 公式计算真实距离，剔除超出范围的点；
* 排序与截断：如果指定了 `ASC` 或 `DESC`，Redis 会对结果按距离排序；如果指定了 `COUNT`，则截取前 n 条。带 `ANY` 时，满足数量即提前结束扫描，不再保证结果最近；

范围查询的复杂度为 **O(N + log M)**：

- M：key 中的元素总数，对应跳表定位区间的开销；
- N：9 个格子覆盖范围内的候选元素数，也就是需要逐一计算距离的元素数量。

**影响性能的主要因素是候选点的密度**，而不是 key 的总大小。在热点区域用大半径搜索会扫描大量元素，这是使用时需要重点注意的地方。

# 4. 最佳实践

**避免大 Key**

把全国所有点放进同一个 key 会带来两个问题：

- 单 key 过大，迁移、删除、持久化时可能阻塞 Redis；
- 在集群模式下，一个 key 只能落在一个分片上，造成热点。

建议按城市或区域拆分 key，例如 `geo:shops:{cityCode}`，也可以按粗粒度的 GeoHash 前缀分桶。

**member 只存 ID**

member 只存 ID，详细信息（名称、评分、营业状态等）存到 Hash 或其他存储中，查出 ID 后再批量获取。

这样既能减少 GEO key 的内存占用，也能避免 member 随业务字段变化而频繁变动。

**查询限制结果数量**

范围查询一定要带 `COUNT`，并控制搜索半径。分页场景可以使用 `GEOSEARCHSTORE ... STOREDIST` 把结果暂存，再用 `ZRANGE` 分页读取，并给暂存 key 设置过期时间。

**能力边界**

Redis GEO 只支持**点**数据，以及**圆形和矩形**检索，不支持：

- 多边形区域判断，例如"某点是否在配送区内"；
- 线、面等复杂几何对象；
- 按道路距离计算，它计算的是球面直线距离；
- 极地区域的坐标。

这类需求应使用 PostGIS、Elasticsearch geo_shape、MongoDB 等专业方案，或者先用 Redis GEO 粗筛，再在应用层精确判断。
